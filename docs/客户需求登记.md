# 客户需求登记

2026-10-28：在独立任务分支 `agent/customer-registration` 实现并完成本地验收。用户随后要求选填详情默认展开，并明确授权完成后部署。发布回执另记，不能仅凭此说明认定已上线。`.com` 保留 `site/com` 原版营销页面，`.net` 保留新版页面。

## 前台入口

中英文分别使用 `/zh`、`/en` 前缀。

| 路径 | 业务 |
| --- | --- |
| `/registration` | 四类需求总入口 |
| `/rental-registration` | 原出租托管登记，字段和 Google 同步流程不变 |
| `/buying-registration` | 买房：区域、总预算、用途、时间；户型、车位与意向房源选填 |
| `/selling-registration` | 卖房：区域、出售时间、期望售价与占用情况；地址、户型、其他中介挂牌情况选填 |
| `/advisory-registration` | 购房咨询、装修翻新、房屋打理、维修维护和其他服务，按服务显示相关字段 |

新增三类仅称呼和一种有效联系方式必填；首选电话、WhatsApp、微信号或邮箱，其他资料可后补。选填详情进入页面默认展开。预算是澳元总金额，未填写与明确填写 0 分开保存。各业务有独立会话草稿与回执；不将客户联系方式放入 URL。保存结果不明确时锁定同一次请求并允许重试，避免重复登记。成功页确认资料已保存并由团队跟进；不再提供电话拨号、微信二维码或 WhatsApp 直联。城市采用后端保存结果。

首页、买卖服务、置业服务和房源详情补充对应入口，保留短咨询。当前短咨询成功后可选择“继续补充详细需求”，通过页面导航状态关联原咨询；后端同时核对联系方式及城市。不会仅凭姓名或联系方式自动合并客户。原版 `.com` 营销包保持原样，由已有 `com-contact-email.js` 补充资料登记链接；该补丁不读取表单、拦截请求或发送 API。`.com` 当前独立页面构建携带 `data-site="com"`，防止预览或返回首页时串用新版设计。

## 后台与权限

`/admin/registrations` 统一查看新三类与原出租记录，可按业务、城市、状态筛选并搜索称呼或联系方式。原 `/admin/rental-registrations` 继续用于出租资料和原 Google 同步设置。

新增登记支持跟进状态、负责人、内部备注、下次联系时间和版本并发检查。买房与购房咨询之间可调整跟进分类，原填写内容保留。日期在列表和详情中以北京时间显示；编辑下次联系时间时明确使用设备当地时间。

管理员可查看全部；城市负责人和助理仅可查看匹配城市的记录，未知城市仅管理员可见。助理不得改负责人；负责人必须具备该城市访问权限，邮件账号不能访问登记。显式关联的短咨询可从后台打开。

## 数据和接口

- `POST /api/customer-registrations`：Node 与 Worker 共用严格字段校验。首次 201、相同 requestId 与内容重试 200 且回执相同，内容冲突 409。只返回回执、创建标识与后端城市，不提供公开记录查询。
- `GET /api/admin/customer-registrations` 与 `GET/PATCH /api/admin/customer-registrations/:id`：鉴权及城市校验、跟进版本检查。资料查询最多返回最近 1000 条，界面明确显示这一范围；出租模块另取最近 1000 条。
- 新增 `0019_customer_registrations.sql`，独立 `customer_registrations` 表。保留原出租表、通知队列、分流游标及历史资料。SQLite 本地启动执行迁移；未来发布前须先备份并单独安排 D1 的 0019 兼容迁移，构建不会迁移线上数据库。
- 原短咨询关联基于不可预测 requestId 加联系方式及城市核对；登记不会新增一条短咨询、自动合并其他需求或发送机器人通知。
- 来自房源详情的 `propertyId` 必须对应已发布在售房源；城市、地址由服务器读取，不能信任 URL 中的城市。相同请求重试可在房源下架后取得原回执，不重复登记。外部意向房源地址仅作为文字保存，不自动抓取 URL。
- 2026-10-29 修复：新三类也进入 Google 自动同步，使用同一文件的“卖房登记”“买房登记”“置业服务登记”三个独立工作表；出租原表及共享权限保留。0020 迁移为已有三类登记补建同步队列，不要求客户重新提交。原始类型决定目标工作表，调整买房/购房咨询分类只更新“当前需求分类”，不移动或复制记录。同步使用记录编号去重、RAW 值、租约及版本检查；网络结果不明至少等待5分钟后重试，最多5次后提示管理员。每分钟处理，后台显示同步状态及管理员重试入口；跟进状态/分类变更会排队，内部备注、负责人和下次跟进时间不写入共享表。

## 本地预览与检查

先分别运行 `npm run build:com`、`npm run build:net`，再运行：

```powershell
node --import tsx scripts/customer-registration-local-review.ts
```

原版 `.com` 预览：http://127.0.0.1:5273/zh/registration 。新版 `.net` 预览：http://127.0.0.1:5274/zh/registration 。模拟后台说明及测试账号只在本机 `/__local` 页面提供。

预览仅监听 127.0.0.1，使用 `data/local-review/customer-registration/fixture.sqlite`，不读取正式数据库；关闭真实通知、邮件和表格同步，并阻止服务器出站请求。模拟记录明确标为本地演示。该脚本不启动通知投递定时任务，也不更改正式账号或线上配置。

验证包括 Node/SQLite 及真实 workerd/D1 的输入校验、并发去重、来源校验、城市隔离、跟进冲突、负责人权限、房源权威信息与原短咨询关联。`npm test` 中原房源验收依赖未入库的 `data/market-reference.json`、`data/viewing-source`、发布媒体和审核证据；新 worktree 需安全取得这些现有测试资料，不能将缺失素材误报为代码测试通过。浏览器验收覆盖中文各分支保存、回执刷新、英文显示、320/390px 布局、两站独立样式和后台跟进。
