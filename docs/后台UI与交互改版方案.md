# 后台 UI 与交互改版方案

状态：已完成可审阅本地版本，尚未经 Claude 审阅。未发布、部署或提交推送。当前实现复用真实 API；浏览器验收以拦截 API 和临时测试库隔离，不修改真实客户记录、顺序、游标或统计。

## 信息结构与实现

- 登录：橘白简洁表单，授权成员说明，输入标签、加载与失败提示，沿用后台邮箱登录。公网页面仍无邮箱选项。
- 框架：桌面侧边导航与账号栏；手机品牌/语言/账号菜单、紧凑图标导航。页面为概览、咨询、房源、团队账号、渠道分流。经理与助理只见原有权限允许的三个业务入口；管理员专属页面直接访问也显示权限提示，服务端权限保持不变。
- 概览：真实 API 的咨询总数、待联系、已发布房源、通知待送数量；跟进列表直接进入对应咨询。不添加图表、假增长或示例业务数据。
- 咨询：搜索、服务组/服务/顾问/状态筛选进入 URL；语言切换和详情打开不丢搜索。桌面表格、手机摘要与独立跟进按钮。原生模态详情隔离背景，Escape关闭并恢复焦点；联系方式直接可见，原始档案独立展开，跟进状态、负责人、日期、备注和保存保持原接口。
- 房源：地址/标题/城市搜索、状态和发布筛选；手机直接看价格、发布状态和编辑操作。编辑页保存/返回固定在顶部，图片、导览、事件和原有校验保留；不扩展权限。
- 团队账号：原账号、角色和城市范围列表；新增表单按需打开，角色与负责城市清楚，管理员城市控件禁用，取消清除密码。未增加修改角色、重置密码等现 API 不具备的业务功能。
- 渠道分流：WhatsApp 与微信两个独立简表标签页，默认只显示顺序、后台组名、号码/二维码、启用及必要操作。统计另页签，不堆分组表单。二维码只预览码体与白边，后台不打开真实 WhatsApp 或提前消耗分流。

## 排序的实际规则

每个渠道可自由跨组拖动，组只是标签，组 ID/名称不因排序改变。触摸与鼠标都只在拖柄接管手势，其他位置保持纵向滚动；提供方向键及上下移动按钮。行顺序即轮询顺序，停用目标跳过；保存前是草稿，有未保存、保存中、成功、失败和显式还原反馈。保存失败保留草稿供重试，还原可恢复最后一次确认的配置。

新增可选 JSON 字段 `queueOrder`（每渠道从0编号），使用既有 `reception_targets.position` 持久化，Node SQLite 与 Worker D1 共享逻辑；无需新增数据库表或迁移。旧配置没有该字段时仍按 `groupOrder/targetOrder`，兼容既有导入。排序保存不重置游标、目标ID、启停、历史分配或事件快照。后续轮次以原累计游标在新队列中继续，不重分配已有访问。

实际本地配置保持7个WA号码和6张微信二维码，江鹏/江牧/江承裕三组。不按人配对。访问分配、按钮点击、二维码展示分开统计，明确不等于聊天或加粉；组和目标明细、时间、咨询关联仍可查。

## 验收与证据

- `admin-before-*` 为原界面参考，`admin-after-*` 为本地改后截图；浏览器中使用明确 Fixture 资料，不代表真实业务数据。
- `admin-ui-results.json`：390/768/1280，中英五后台页面、登录、详情/编辑器、二维码预览；鼠标或CDP触摸拖动、键盘移动、两个池隔离、保存刷新、错误还原、角色可见功能；无横向溢出或页面脚本错误。
- `admin-ui-edge-results.json`：隔离登录失败/成功、账号创建、房源保存、语言保留筛选、模态焦点、空态/错误/加载；写请求全部 mock。
- `server/reception.test.ts`：临时 SQLite 与实际 Miniflare D1 验证自由队列顺序、启停、并发/幂等、独立游标、重排保留历史/事件及鉴权。
- 浏览器脚本保存在 `scripts/admin-review/`，从项目目录运行 `node scripts/admin-review/pages.cjs` / `states.cjs` / `service-copy.cjs`；需本地5173和Edge，不读取管理员密钥，不访问真实客户写接口。浏览器mock任何 `/api/**`，服务页脚本禁止咨询POST。
